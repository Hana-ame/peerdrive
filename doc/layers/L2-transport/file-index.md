# File Index Persistence (file_index.go)

> One-line responsibility: local file index service — sha256 → absolute path mapping (SQLite
> persisted), supporting the frame protocol's six create/upload/list/info/delete/sync verbs and
> incremental sync (seq cursor + tombstone).

## Responsibilities

`FileIndexService` is a data-plane component of the frame protocol layer (belongs to LAYERS ⑤ data aspect, held and used by the ② frame protocol layer): it maintains the "content hash → local absolute path" mapping and is the path resolution source for `req` fetches (download looks up the index first, then content-addressed storage).

Three blocks of responsibility:

1. **Registration and query**: `Create` (external file registration, no copy), `List`, `Info`,
   `DownloadPath`, `Delete` (logical delete).
2. **Chunked upload session**: `UploadSession` — 64KB chunk bitmap tracking, concurrent chunking
   from multiple sources, resumable upload, `Complete` (fsync + full-file sha256 + register),
   `Abort`.
3. **Incremental sync**: `SyncSince` (change set after the seq cursor, including tombstones),
   `ApplySync` (merging peer changes into local).

SQLite persistence lives in `internal/repository` (`UpsertFileIndex` / `ListFileIndex` /
`GetFileIndex` / `DeleteFileIndex` / `ListFileIndexSince`); this file does not touch SQL directly.

## Key mechanisms

### Secure root directory (IsPathAllowed, file_index.go:58)

The allowed root directory for create registration = uploadDir (resolved with `filepath.Abs` + `EvalSymlinks` at construction). Judgment: absolute path + `filepath.Rel(rootDir, abs)` after symlink resolution does not start with `..` and is not `..`.

- **Why EvalSymlinks**: to prevent a "symlink inside the root → target outside the root" bypass (H2).
- create outside the root is rejected outright; serveFile also passes the same check before returning an index path.

### Chunked upload session (UploadSession, file_index.go:153)

```
BeginUpload(name, size) → session (idempotent reuse for the same name; size must match, M7)
  - size cap 8GB (against malicious declarations)
  - target file: uploadDir/sanitizeName(name) (prevents path traversal)
  - bitmap: []uint64, 64 chunks per word — allocated as (totalChunks+63)/64
    (pitfall: it was once allocated by chunk count, which broke the last-word fullness logic)
  - resume: existing file size → rebuild the bitmap, treating [0, min(size, fsize)) as written
    (pitfall: holes/out-of-order writes may wrongly mark as written; Complete's final sha256 check catches it)

WriteAt(offset, data) → write to disk + set bits by byte range (one write may cross a chunk boundary)
  - out-of-range offset (offset<0 or offset+len > size) is rejected
  - aborted / handle removed → explicit error (M7 race fix)

ContiguousOffset() → the starting byte of the first unset chunk (the resume starting point)

Complete() → full-bitmap check:
  - full → file.Sync() → hashFile(full-file sha256) → UpsertFileIndex → return FileInfo
  - not full → (false, nil, nil) (not registered)
  - fullness-check pitfall: all words except the last need all 64 bits; the last word only needs
    (total chunk count mod 64) bits — a wrong tail-chunk-fullness check once caused perpetual incompleteness

Abort() → idempotent abort + delete the target file (calling it after reap removes the handle has no side effects)
Close()  → close the handle without deleting the file (preserves resume)
```

- **Multi-source semantics**: multiple connections/nodes concurrently `WriteAt` different chunks; the bitmap merges, and fullness means complete (the requester of the last chunk receives uploaded).
- **Session key = the sanitized file name**, not the hash — the chunked upload target is determined by name, and the hash is computed from the content at completion.

### Session reaping (reapUploads, file_index.go:74)

`NewFileIndexService` starts a goroutine that scans `s.uploads` every 5 minutes: 10 minutes without activity →
mark `aborted` + remove the handle + close + delete the file (against disk exhaustion). M7 fix: holding `sess.mu`
for judgment + marking + removal is serialized with `WriteAt`/`Complete` — previously it unlocked first then Aborted,
leaving a check window (after being judged idle, but before Abort, concurrent chunks got an already-closed handle → upload failed for no apparent reason).

### Incremental sync (SyncSince / ApplySync, file_index.go:396,416)

```
SyncSince(since) → rows = ListFileIndexSince(since) → []FileInfo + lastSeq
  - FileInfo.Delete marks a tombstone (from the repository's deleted field)
  - lastSeq = max(all row.Seq, since)
ApplySync(files) → one by one: Delete=true → DeleteFileIndex (tombstone);
  non-empty Path → UpsertFileIndex; illegal hash is skipped (defending against peer dirty data)
```

Sync model: `file_index.seq` monotonic cursor (generated by the repository layer), `sync{seq}` gets incremental
changes (including tombstones), the peer's `ApplySync` merges them — **delete tombstones must carry an order**
(L6: the old implementation discarded DeleteFileIndex's seq, so the peer's sync could not track delete events).

### Others

- **LIMIT defense for List** (file_index.go:344): limit comes from the remote list verb (arbitrarily
  large); passing it straight into SQL LIMIT would materialize the whole table → memory DoS. Clamp to
  [1, 1000] (the repository layer only guards limit<=0).
- **hash validation for Info/Delete**: `IsStrictSHA256` first, preventing dirty hashes from reaching SQL.
- **sanitizeName** (file_index.go:453): `filepath.Base` + backslash normalization, empty name falls back to
  "upload.bin" — prevents path traversal (`../../x` → `x`).
- **hashFile**: full-file streaming sha256 (large files do not reside in memory).

## Pitfalls and design decisions

1. **H2 arbitrary file read** (IsPathAllowed/Create): the old create implementation accepted any absolute path, so a peer could `create /etc/shadow`, get the hash, then `req` to read it. Fix: root anchoring +
   EvalSymlinks resolution + `filepath.Rel` prefix check; symlink escape (symlink inside the root → target
   outside) must be rejected (TestFileIndex_CreateSymlinkEscape).
2. **Bitmap allocation granularity** (BeginUpload, file_index.go:196): `[]uint64`, 64
   chunks per word — it was once allocated by chunk count, which broke the last-word fullness logic
   (for boundary `bits < 64`, the `(1<<bits)-1` mask is key to correct fullness checking).
3. **Last-word fullness** (Complete, file_index.go:274-290): all 64 bits for every word except the last;
   the last word only requires the actual chunk count — a wrong tail-chunk-fullness check once caused perpetual incompleteness.
4. **M7 race** (reapUploads + aborted): reap unlocked after judging idle, then Aborted, leaving a check
   window (concurrent WriteAt got an already-closed handle → upload failed for no apparent reason). Fix: complete
   judgment + marking + removal while holding sess.mu; WriteAt/Complete report an explicit error on `aborted`.
5. **M7 same-name session size mismatch** (BeginUpload, file_index.go:183): the bitmap was built for the old size;
   a size declaration mismatch would break resume offsets and last-chunk fullness. Fix: reusing the same name requires
   a matching size, otherwise reject.
6. **Imprecision of resume** (file_index.go:206-219): after a process restart, the bitmap is approximately rebuilt
   from file size (holes/out-of-order may wrongly mark as written) — the final Complete sha256 check catches it
   (a content mismatch fails the whole operation and does not register a wrong mapping).
7. **Empty file** (size==0): the bitmap is naturally full (totalChunks=0, the loop does not execute, full stays
   true) — sha256(empty) is a legal content-addressed value; the upload side must be able to complete.
8. **Ordered tombstones** (Delete returns seq, L6): incremental sync's delete events must be trackable by the peer's
   cursor, otherwise the peer permanently retains the mapping of deleted files.
9. **list LIMIT 1000 cap**: a remote may send any limit — this defends against whole-table materialization memory DoS while
   leaving room for pagination semantics (offset cursor).

## Tests

All in `file_index_test.go` (13 tests); `initTestDB` uses an in-memory SQLite (the file_index
table is created with InitDB).

| Test | Background of discovery |
|---|---|
| `TestFileIndex_CreateAndInfo` (:26) | **Functional test**: create only indexes absolute paths, no file copy; registration outside the root must be rejected (H2); illegal hash rejected |
| `TestFileIndex_CreateSymlinkEscape` (:60) | **H2 defensive test**: IsPathAllowed must resolve with EvalSymlinks before judging, otherwise a "symlink inside the root → target outside" bypasses the restriction |
| `TestFileIndex_IsPathAllowed` (:74) | Root directory judgment: inside the directory allowed, outside the root rejected |
| `TestFileIndex_UploadStream` (:86) | **Functional test**: WriteAt chunking (64KB blocks) + full-bitmap check + sha256 registration + readable content |
| `TestFileIndex_UploadEmpty` (:123) | **Asymmetry between the two ends**: the fetch side's hashMatchesSHA256 already supported empty files, but the upload side's old implementation rejected size<=0 outright — sha256(empty) is legal, and the size=0 bitmap should be naturally full |
| `TestFileIndex_UploadSizeMismatch` (:142) | **Defensive test**: size is a protocol trust boundary — over-cap rejected (9GB), out-of-bounds write rejected (declared 100, wrote 200) |
| `TestFileIndex_ListAndDelete` (:161) | **Functional test**: list + logical delete (tombstone) → no longer in the list; delete returns a new seq (L6) |
| `TestFileIndex_SyncSince` (:189) | **Functional test**: metadata sync depends on the monotonic seq cursor; ApplySync merges idempotently; delete tombstones sync effectively (paths synced verbatim) |
| `TestFileIndex_UploadMultiSource` (:242) | **Functional requirement**: multiple nodes upload different chunks of the same file in parallel — 4 sources write concurrently out of order, the bitmap merges, and the last chunk triggers completion |
| `TestFileIndex_UploadResume` (:286) | **Functional requirement**: reopen the session after interruption, ContiguousOffset's contiguous written offset is correct, and the remainder is completed from the resume point |
| `TestFileIndex_UploadPartialNotComplete` (:316) | **Defensive test**: when chunks are missing, Complete returns incomplete and must not register a mapping |
| `TestFileIndex_BeginUploadSizeMismatch` (:334) | **M7 defensive test**: a same-name session declaring a mismatched size must be rejected (bitmap built for the old size → broken resume offsets); a match allows reuse |
| `TestFileIndex_AbortIdempotent` (:349) | **M7 defensive test**: Abort and reap's handle removal may race; it must be idempotent; writes after abort must fail explicitly (rather than a confusing failure from writing a closed handle) |

# DHT 作为节点发现层的可行性与边界评估报告

> 对应 Issue: #146  
> 状态: 调研评估完成，决策明确：**否决将 DHT 作为节点发现层；保留 DHT 用于 #121 metadata 存储寻址**  
> 关联 Issue: #147 (多通道发现聚合), #89 (节点准入控制), #90 (发现层外移), #121 (metadata 内容寻址化), #115 (架构总纲)

---

## 1. 核心前提厘清：现有 DHT 的真实能力定位

Peerdrive 仓库中的 `back/p2p_bt` 模块基于 BitTorrent DHT 规范，但其定位**不是节点发现，而是去中心化 KV 数据存储**：
- **BEP 44**：实现 $\le 1000$ 字节的不可变（Immutable，SHA-1 寻址）与可变（Mutable，Ed25519 公钥签名寻址）数据读写；
- **BEP 51**：实现 InfoHash 采样；
- **现状**：
  - `PEERDRIVE_BT_DHT_ENABLE` 默认关闭（`false`）；
  - 代码注释明确标注：「`DHT init blocks startup`」（初始化阻塞主线程启动）；
  - `bep44.go` 明确指出：「`most DHT nodes do not support BEP 44 arbitrary data storage`」（公网 Mainline DHT 节点大部分不支持或限制任意 BEP 44 数据持久化）。

因此：**利用 DHT 进行节点发现并非「完善现有逻辑」，而是引入一套全新的 P2P 发现机制。**

---

## 2. 差距与可行性全景评估

### 2.1 发现层可行性：公网 DHT vs 节点公告
| 维度 | Mainline DHT (BEP 5 / BEP 44) | 现有信令 / HTTP / MQTT 发现 |
|---|---|---|
| **网络类型** | 全球公网 BitTorrent Mainline DHT | 自托管 / 私有房间 / 授权信令 |
| **持久性与 TTL** | 极低（节点离线或路由桶刷新后数据迅速丢失，通常 2 小时失效） | 高（HTTP 心跳 30s，离线即时感知） |
| **成功率** | 极度不可靠（公网大多数节点拒绝或丢弃非 BT 种子存储请求） | 确定性（100% 成功交付） |
| **发现时延** | 分钟级（Kademlia 递归查找通常需 5~30 秒） | 毫秒 ~ 秒级（HTTP 轮询 10s，MQTT 实时推送） |

### 2.2 隐私泄露与准入控制的根本哲学冲突（与 #89 冲突）
1. **明文公网暴露**：
   - BitTorrent DHT 是明文 UDP 协议。全球存在成千上万的 DHT 爬虫（如 `dhtcrawler`、安全扫描探针）。
   - 若将 Peerdrive 节点信息（IP、端口、PeerID）公告至公网 DHT，所有节点的网络拓扑与在线活动均被公开监听。
2. **准入控制崩溃**：
   - Peerdrive 采用预共享密钥（`PEERDRIVE_PSK`）、好友名单与私有房间保障节点私密性（参见 `doc/NETDISK.md` §9）。
   - DHT 的无准入、匿名广播特性与 Peerdrive 的防爬虫、防未授权扫描目标产生**不可调和的冲突**。

### 2.3 启动阻塞与网络环境鲁棒性
1. **启动阻塞瓶颈**：
   - 加入公网 DHT 需要向 Bootstrap 节点（如 `router.bittorrent.com`）发送大量 UDP `ping` / `find_node` 查询建立路由表。
   - 在弱网、移动网络或企业内网环境下，UDP 丢包与防火墙拦截常导致启动过程卡死 10~30 秒。
2. **IPv6 与 NAT 穿透缺陷**：
   - 现有 `p2p_bt` 仅监听指定端口（默认 `:6881`），缺乏 STUN/UPnP 端口自动映射与 IPv6（BEP 32）双栈能力。

### 2.4 安全性：防毒化与女巫攻击（Sybil Attack）
- 公网 DHT 容易受到女巫攻击与日蚀攻击（Eclipse Attack）。恶意攻击者可以生成大量与目标 Hash 临近的虚假 Node ID，劫持路由路径，返回伪造的节点地址或丢弃查询请求。
- 虽然可变数据支持 Ed25519 签名验证，但无法防御拒绝服务（DoS）与日蚀隔离。

## 3. 最终决策与定位建议

### 3.1 明确决策：放弃 DHT 作为节点发现通道
**综合结论：强烈建议放弃将 BitTorrent DHT 作为节点发现层。**
- **投入产出比极低**：在信令 + HTTP 发现 + MQTT 房间已完全解决多节点互联的前提下，引入 DHT 发现带来极高的网络不可靠性与维护成本。
- **严重违背安全基线**：破坏 #89 节点准入控制与私密部署边界。

### 3.2 真正价值归宿：作为 #121 的元数据去中心化寻址层
现有 `p2p_bt` 模块的最佳应用场景不是节点发现，而是**内容元数据（Metadata）的抗审查持久化与可变指针寻址**：
1. **不可变数据（Immutable）**：
   - 基于 BEP 44 将合集的元数据快照（Snapshot Hash / CID）存入 DHT，实现无需任何中心服务器的内容去中心化备份。
2. **可变指针（Mutable Pointer）**：
   - 使用节点的 Ed25519 公钥作为可变键，发布合集最新版本的 Root Hash 指针。用户即使全部信令服务器失联，依然能通过公钥从 DHT 解析出合集的最新内容哈希。

## 4. 后续任务规划

1. **解耦启动阻塞**：
   - 优化 `back/p2p_bt` 的初始化逻辑，将其调整为完全后台异步执行，确保即使开启 `PEERDRIVE_BT_DHT_ENABLE=true` 也绝不阻塞主服务启动。
2. **聚焦 #121 内容寻址**：
   - 将 `p2p_bt` 封装为 `MetadataStorage` 适配器，专用于元数据与指针的发布与检索，不参与实时发现通道。

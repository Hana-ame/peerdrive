# 翻译任务的硬约束（subagent prompt 模板）

> 这份模板是 2026-10-03 一次真实事故的产物。那批"中译英"提交里，翻译 agent
> 顺手改坏了 16 个文件的运行时行为，CI 从 2026-09-27 起连续全红。
> **把下面的约束原样交给任何做翻译的 subagent**，不要压缩成"注意别改坏代码"。

---

## 可直接粘贴的 prompt

```
你的任务：把仓库里的中文翻译成英文。

硬约束（违反即视为任务失败，不是"风格建议"）：

1. 只改这三类文本：
   - 注释（// /* */ # 开头，以及它们的续行）
   - 文档（.md / .txt / .svg 里的说明文字）
   - 用户可见文案：UI 文本、按钮标签、提示语、面向运维的错误消息

2. 绝对不许改（哪怕它看起来像可以顺手优化的地方）：
   - 标识符：变量名、函数名、参数名、结构体字段名、常量名、包名、文件名
   - 协议字段：帧协议 verb（req/meta/data/done/err/create/upload/...）、
     JSON 键名、HTTP 路由、query 参数、header 名、SQL 语句
   - 数值字面量：端口号、长度、超时、权限位（0o600）、魔数、常量表
     （例如 SHA-256 的 K 表——删掉一个常量会让所有内容寻址校验失败）
   - 测试断言里的期望值：assert.Contains / require.Equal / 正则的 pattern
   - 任何控制流：if/for/switch 的条件、return、error 的传播路径、
     并发与锁的时序、超时与重试、校验分支
   - 函数签名、导出的 API、类型定义

3. 错误消息如果被测试或脚本断言：
   改消息之前先搜一遍这个字符串被谁引用了（错误文案经常同时出现在
   测试断言、正则、脚本判据里）。要么三处一起改且改得完全一致，
   要么别改。分别翻译消息和它的断言，是最容易出这种错的地方。

4. 不许"顺手改进"：
   不许重排代码、不许删"看起来没用"的分支、不许把两行合并、
   不许改缩进或空行、不许新增你认为是 bugfix 的东西。
   如果你发现一个疑似 bug，写进报告，不要动手。

5. 不许凭空新增内容：
   测试用例、参数、表格行、注释里的说明，都只能翻译，不能新写。
   （真实事故里翻译给一个测试表凭空造了一个用例，还重复了已有的一个。）

交付要求：
- 按文件分批提交，不要一个巨型提交。
- 提交信息里列出这一批动了哪些类别的文本。
- 完成后报告：动了多少文件，其中哪些属于"绝对不许改"的清单——
  如果非空，说明越界了，必须说清楚。
```

## 为什么这些约束不是洁癖

2026-10-03 那批翻译的实际战果（`0713b38..93889b1`，369 个改动文件）：

| 越界类型 | 实例 | 后果 |
|---|---|---|
| 改标识符 | `p.bitswapFetcher` → `p.bitsswapFetcher` | 字段不存在，编译失败 |
| 改标识符 | `localID, err :=` → `localID, terr :=` | 编译失败 |
| 改字面量 | `"path/filepath"` → `=path/filepath` | 编译失败 |
| 改字面量 | 复合字面量结尾 `}` → `)` | 编译失败 |
| 改字面量 | `'the server's …'` 单引号串里混入撇号 | 整个文件解析失败 |
| 删功能 | 面板分享链接出口整块消失 | 10 个契约测试失败 |
| 删功能 | 连接时 `id: myId` → `id: uid()` | **面板稳定身份没了，private 内容永远取不到** |
| 改协议可见行为 | 面板 id 前缀 `pd-panel-` → `p-` | **用户浏览器旧 id 与运营者好友名单失配，private 权限静默失效** |
| 改安全检查 | 取文件时 `IsPathReadable` 授权检查消失 | 路径边界失守 |
| 改安全检查 | 下载内容 sha256 校验被删 | 内容寻址失去校验 |
| 改安全检查 | 状态文件权限 `0o600` → `0644` | 文件变 world-readable |
| 改输入清洗 | `strings.TrimSpace(peerID)` 删除 | |
| 改导出的 API | `NewPeerJSService` 加参数、`AddForwardRule` 不再返回 error | 调用点不一致 |
| 改测试数据 | 凭空新增测试用例 + 重复已有用例 | 测试数量对不上，意图丢失 |
| 改断言与消息不一致 | 消息译成 `exceeds this node's limit`，断言译成 `cap` | 测试失败 |

## 怎么自己查有没有越界（不跑测试的查法）

审计一批翻译改动时，按"是否影响运行时行为"判定，不要按文件类型：

1. 把改动前后的文件**整份**做归一化：剥掉注释内容、剥掉字符串字面量内容、
   剥掉模板串的文本部分（保留 `${...}` 插值，那里面是代码）。
2. 归一化后逐行比对。**完全一致** = 只改了注释/文案，安全。
3. 有差异 = 动了可执行代码，逐条看差异是标识符、协议字段、数值还是控制流。

⚠️ 两个必须注意的坑：

- **多行注释的续行**：逐行处理时会漏掉 `/* ... */` 中间那些以 ` * ` 开头的行，
  必须整文件扫描后再归一化，否则会产出大量假阳性。
- **字符串也是断言对象**：归一化会认为"改字符串值"是安全的，但如果某个测试
  断言了这个字符串，它就不安全。第 3 条约束就是为这个准备的。

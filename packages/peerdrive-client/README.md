# peerdrive-client

peerdrive's **pure browser consumer**: connect to a peerdrive node, list its shared content, and pull files back.

Zero dependencies, pure ESM, transport-agnostic. Corresponds to the requirement "webrtc pure client consumer, can pull files from this p2p network" --
a single static page is enough to use, no local backend needed.

```js
import Peer from 'peerjs'
import { connectToPeer } from 'peerdrive-client'

const client = await connectToPeer(Peer, 'peerdrive-1a2b3c4d', {
  peerOptions: { host: '0.peerjs.com', port: 443, secure: true },
})

const snap = await client.shares()            // { collections, files, dirs, total }
await client.saveAs(snap.files[0].hash, 'a.bin')   // pull it down and save locally, sha256 verified
client.close()
```

Don't want a bundler? Just put the `peerjs` CDN `<script>` first, then use the global `Peer` inside `type="module"`
-- `demo/consumer.html` does exactly that.

The ready-to-use artifact is the **[public panel `dist/panel.html`](#public-panel-the-netdisk-ui-form-distpanelhtml)**:
single file, no local server needed, double-click via `file://` and it works, generated by `npm run build:panel`.

## The problem it solves

A peerdrive node (the Go service in `back/`) is both holder and consumer: nodes interconnect using the same frame protocol.
But a client that "just wants to grab a file" shouldn't be forced to deploy a Go node. This package separates the consumer side from the server side:

| Scenario | What to use |
| --- | --- |
| Node <-> node interconnection, mutually serving content | The Go service in `back/` (same frame protocol) |
| Browser <-> node, pulling files | **This package** |
| Browser <-> node, loading URL resources (img/video) | `packages/peerdrive-media` (a different url/meta protocol, aimed at media elements) |

## Installation

This package has zero runtime dependencies. `peerjs` is provided by the caller (not written into `dependencies`, to avoid bloating the consumer's bundle size).

```bash
npm i peerdrive-client
```

## Quick start

### 1. One-step setup (recommended)

```js
import Peer from 'peerjs'
import { connectToPeer, ERR } from 'peerdrive-client'

const client = await connectToPeer(Peer, nodeId, {
  peerOptions: { host, port, path, key, secure },
  connOptions: {},              // passed through to peer.connect, usually no need to change
  idleTimeoutMs: 120_000,       // how long without receiving a frame for this request before declaring it dead
  maxBufferBytes: 256 << 20,    // memory gate for fetch/saveAs
  psk: '',                      // fill in the same key when the node has PSK gating enabled (see below)
})
```

**Pre-shared key (PSK)**: a node can set a gate with `PEERDRIVE_PSK`; once set, the peer must present the same key on the connection
or all requests return `err` (`code: 'PSK_REQUIRED'`). When `psk` is given,
this package sends it immediately as the first frame after the connection is established (DataChannel is in-order, so no need to wait for a receipt,
nor does it add an extra RTT to the connection). Not given = not presented; when the peer hasn't enabled the gate, the two are indistinguishable.

```js
import { connectToPeer, ERR } from 'peerdrive-client'

try {
  const client = await connectToPeer(Peer, nodeId, { psk: 'demo-psk' })
} catch (e) {
  // if intercepted while getting the manifest/file, e.code === ERR.PSK_REQUIRED, prompt to fill in the key
}
```

`client.pskState` reflects the handshake state: `none` (not configured) / `sent` (presented, awaiting receipt) /
`ok` / `err` (`client.pskError` is the peer's msg).

Internally equivalent to: build Peer -> wait for signaling `open` -> `peer.connect(nodeId, { serialization: 'raw' })` -> wait for DataChannel `open`.

> ⚠️ `serialization` must be `'raw'`. Only in raw mode does `string` go over a text frame and `ArrayBuffer` over a binary frame,
> which reproduces the Go side's "text frame = JSON header / binary frame = data block" semantics. Using the default `binary` serialization would have
> peerjs's own chunker wrap the data blocks, and the peer couldn't parse them. `connectToPeer` already sets this, don't forget it when writing by hand.

### 2. Self-managed connection (existing PeerJS connection / different transport)

```js
import { connect } from 'peerdrive-client'

const conn = peer.connect(nodeId, { serialization: 'raw' })   // or any object satisfying {on,send,open,close}
const client = await connect(conn, { idleTimeoutMs: 60_000 })
```

## API

### `connectToPeer(PeerCtor, peerId, opts?) -> Promise<PeerDriveClient>`
Builds signaling + dials + waits for ready. `PeerCtor` is the PeerJS `Peer` constructor (this package does not import peerjs).

### `connect(conn, opts?) -> Promise<PeerDriveClient>`
Wraps an already-established connection. `conn` only needs to satisfy `{ on(type, cb), send(data), open?, close?() }`.

### Client instance

| Member | Description |
| --- | --- |
| `ready(timeoutMs?)` | Wait for connection ready; resolves immediately if already ready |
| `isOpen` | Whether it is ready |
| `peerId` | The peer's id (read from the connection) |
| `shares({timeoutMs?})` | Query shared manifest -> `{collections, files, dirs, total, peerId}` |
| `put(data, opts?)` | **Local ingest**: send content into the node -> `{hash,size,name,path}` |
| `pull(url, opts?)` | **Network ingest**: have the node fetch this URL for you and ingest it -> `{hash,size,name,path}` |
| `stream(hash, opts?)` | **Async iterator**, yields `Uint8Array` block by block (does not reside in memory) |
| `fetch(hash, opts?)` | Fetch whole `Uint8Array` (subject to `maxBytes` limit) |
| `fetchBlob(hash, opts?)` | Fetch as `Blob` (guesses MIME by filename) |
| `fetchText(hash, opts?)` | Fetch as utf-8 text |
| `saveAs(hash, filename?, opts?)` | Triggers a browser download; returns byte count |
| `saveShare(item, opts?)` | Save directly from a manifest entry (auto-picks filename) |
| `stats` | `{requests, chunks, bytes, failures}` |
| `close()` | Closes the connection (destroys any Peer it built itself) |

opts for `stream` / `fetch`:

| Option | Default | Description |
| --- | --- | --- |
| `offset` | `0` | Start offset (range request) |
| `size` | `-1` | Read length, `-1` = to end of file |
| `maxBytes` | `256MB` | Memory gate, exceeding throws `TOO_LARGE` |
| `onProgress(received, total, hash)` | -- | `total` of `-1` means the peer did not declare a size |
| `signal` | -- | `AbortSignal`, can be cancelled |

### Streaming pull (large files)

```js
let received = 0
for await (const chunk of client.stream(hash)) {
  received += chunk.byteLength
  await fileHandle.write(chunk)     // File System Access API / StreamSaver / write directly to disk
}
// the full request has sha256 verified on completion, mismatch throws HASH_MISMATCH
```

`stream()`'s blocks go only into a **bounded queue**; if the consumer doesn't take them, backpressure forms naturally; breaking early cancels that request
(later-arriving frames are discarded).

### Write direction: putting content into the node

```js
// local ingest (Uint8Array / ArrayBuffer / Blob / File / string)
const { hash } = await client.put(fileInput.files[0], {
  onProgress: (sent, total) => console.log(`${sent}/${total}`),
  signal: abortCtrl.signal,   // cancellable: lets the in-flight round end immediately with CANCELLED
})

// network ingest: have a node with network capability fetch this address and ingest it for you
const got = await client.pull('https://example.com/some.zip', { name: 'some.zip' })

// successful ingest != retrievable -- pull once by hash and recompute sha256 to close the loop
const bytes = await client.fetch(got.hash)
console.log(await PeerDrive.sha256Hex(bytes) === got.hash) // true
```

Two hard constraints: **one connection can only have one upload stream at a time** (serialize multiple files, parallelism will
receive `already in progress` on the second); `put` first reads the entire content into browser memory before chunking, so
slice very large files yourself.

`pull` is the node's external egress, so it has SSRF protection: only public `http/https` is allowed, intranet/local addresses,
URLs with username/password, and redirects to intranet are all rejected, with a size cap. Such rejections are **expected behavior**,
surfaced as `PEER` errors passing through the node's original message.

### Auto-discovering online nodes

```js
import { discoverNodes } from 'peerdrive-client'

const nodes = await discoverNodes(
  { host: 'signal.example', port: 443, secure: true },
  { coll: 'optional: only search a given collection', timeoutMs: 8000 },
)
// -> [{peerId, lastSeen, nodeType?, collections?, uptime?, loadInfo?}, ...]
```

Goes through the signaling's REST discovery endpoint `GET /discover/nodes`, **does not occupy or depend on any WebRTC connection**
-- you can search even without connecting to a node. The prerequisite is that the signaling is willing to give a cross-origin response: a `file://` page has origin `null`,
and hosting it puts it on another domain; without `Access-Control-Allow-Origin` the browser won't even give a status code,
leaving only `TypeError: Failed to fetch`. `discoverNodes` detects this and names this response header in the error message,
instead of vaguely reporting "search failed".

### Error codes

UI should branch on `err.code`, not match on `message` text.

| code | Meaning | Common handling |
| --- | --- | --- |
| `INVALID_HASH` | hash is not 64-char lowercase hex | input validation, reject locally (no request sent) |
| `TOO_LARGE` | exceeds `maxBytes` / protocol cap 8GB | switch to `stream()` or raise the gate |
| `HASH_MISMATCH` | content does not match hash | discard content and notify (data corrupt/tampered) |
| `INCOMPLETE` | peer's done byte count does not match actual received | retry |
| `TIMEOUT` | idle timeout / verb no response | notify that the other side is offline or network is unstable |
| `CLOSED` | connection closed | reconnect |
| `PROTOCOL` | frame not legal (peer is not a peerdrive node?) | report error, do not retry |
| `PEER` | peer returned an `err` frame (not found etc.) | show the peer's message |
| `CANCELLED` | local cancel (`signal` / iterator interrupted) | silent |

## Protocol

**Character-for-character aligned** with the definition in `back/internal/transport/conn.go` (field names, case, `-1` semantics all consistent):

```
request   {"type":"req","hash":"<64hex>","offset":0,"size":-1,"reqId":"…"}
response  {"type":"meta","hash":"…","total":N,"reqId":"…"}
          {"type":"data","hash":"…","offset":N,"size":N,"reqId":"…"} + followed by size bytes of binary block
          {"type":"done","hash":"…","offset":N,"size":N,"reqId":"…"}
          {"type":"err","msg":"…","reqId":"…"}
share     {"type":"share","reqId":"…"}
          -> {"type":"share-resp","collections":[…],"files":[…],"dirs":[…],"total":N,"reqId":"…"}
```

Three constraints that must not be broken:

1. **The data header is a text frame, the data block is a binary frame**. Sending them backwards makes the peer swallow the JSON as data.
2. **A data header and its data block must be contiguous**. The receiver uses "connection-level expect" -- it attaches the binary block to the request
   belonging to the **most recent** data header, the block carries no `reqId`. So you can't interleave two requests' blocks (the Go side relies on connection-level
   `sendMu` to guarantee `SendFrame` atomicity). This package specifically covers this in tests (see
   "connection-level expect and out-of-order frames" in `test/client.test.mjs`).
3. **Field names character-for-character aligned**. Changing to `req_id` will not error, it will just make the peer fail to route and the request hang to timeout.

## Design trade-offs

**Why transport-agnostic.** `PeerDriveClient` only requires `{ on, send, open, close }`, does not know about PeerJS.
Benefits: the package itself is zero-dependency; tests cover all state machines with a fake connection (no signaling server or real WebRTC needed);
switching to raw `RTCPeerConnection` or WebTransport later does not require touching this file.

**Why we write SHA-256 ourselves.** `crypto.subtle.digest()` is one-shot -- you must accumulate the whole content in memory
before computing the digest, which directly conflicts with "streaming pull". So the streaming path uses a pure JS incremental implementation (`src/sha256.js`),
the one-shot path `sha256Hex()` still prefers WebCrypto. Another benefit is that pure JS does not require a secure context
(https/localhost), so http pages can also use it. The two paths cross-verify in tests.

**Why there is a memory gate.** `fetch()`/`saveAs()` reside entirely in memory (browser downloads can only go through Blob),
a 2GB file would crash the tab directly on a phone. So the default cap is 256MB, exceeding throws `TOO_LARGE` and suggests
switching to `stream()`; when the peer declares a size it is gated at the `meta` stage, no wasted download.

**Why cancel just drops frames.** The protocol has no "cancel" frame (the Go side has no corresponding implementation either), the peer will continue
sending this request to completion. This package's approach is to stop collecting locally and release cached blocks; truly interrupting requires closing the whole connection.

**Why an empty manifest from `shares()` is not an error.** The other side not enabling external sharing is a legitimate business state
(`PEERDRIVE_SHARE_ENABLE` defaults to off); UI should render "this node has no shared content" rather than a red error.

## Public panel (the netdisk UI form: `dist/panel.html`)

The netdisk **has no local HTTP-server-style UI** -- the UI is a **public static panel**, dialed in via PeerJS.

**Online version: <https://hana-ame.github.io/peerdrive/>** (`.github/workflows/pages.yml`
auto-builds and deploys when panel-related files change). After going live, whether it still works can be verified with one command:

```bash
node scripts/verify-pages.mjs                 # defaults to verifying peerdrive's Pages URL, can pass a URL
# panel skeleton / bundle injection / peerjs retrievable / HTTPS+ws:// mixed content notice / no JS errors
```

```bash
npm run build:panel    # generates dist/panel.html (58 KB, single file)
```

`dist/panel.html` is a **self-contained single file**: client source is inlined, `file://` double-click to open,
or drop it onto any static hosting (Pages / CDN / OSS) as a public URL.
It does not connect to your local backend API, instead it WebRTC-connects directly to the node.

```text
panel.html?node=<peer id>&host=<signaling>&port=&path=/&key=peerjs&secure=0&auto=1
```

- `node/host/port/path/key/secure` prefill connection params -- the link in the address bar is the panel's complete state,
  can be sent directly to others; `auto=1` means connect on open.
- Panel capabilities: multi-node coexistence, shared manifest (files/collections), pull by hash or click,
  transfer task list (progress/rate/cancel), preview (image/video/text).
- peerjs loads via "same-directory `peerjs.min.js` -> jsdelivr -> unpkg" fallback;
  for offline/intranet environments just run `npm run vendor:peerjs` to download it to the `dist/` directory and you need no network at all.

> **Signaling must allow CORS**, otherwise the panel cannot get a temporary id: a `file://` page's origin is `null`,
> the browser will block the `GET /peerjs/id` response, and PeerJS only reports a vague `server-error`.
> Self-hosted signaling `back/signalserver` has already added cross-origin headers and OPTIONS preflight short-circuit on HandleID/HandleAnnounce/HandleLeave/HandleNodes/HandleStatus (`allowCORS`).

> **HTTPS pages can only use wss signaling**. The online version runs on GitHub Pages (forces HTTPS), browsers treat
> `ws://` initiated from an HTTPS page as mixed content and block it, with no notification -- the panel detects this configuration and
> blocks directly and explains how to fix. Self-hosted signaling with wss: `peersignal -tls-cert cert.pem -tls-key key.pem`
> (both parameters must be given as a pair, giving only one errors out), or put a TLS reverse proxy in front.

## Known limitations

- **Large files to disk need caller handling**: `saveAs()` resides entirely in memory; truly large files should use `stream()`
  combined with File System Access API or StreamSaver to write to disk (browsers do not allow `<a download>` streaming writes).
- **No resume**: after a connection drops, re-pulling starts from the beginning. The protocol supports `offset`, resume logic is on the caller side.
- **The `list` frame is not implemented**: `list` is the node's local admin index (includes the local absolute path), open only to trusted peers.
  The consumer only goes through `share` (the operator's explicitly declared sharing scope).
- **Identity verification**: the current protocol does not verify the requester's identity (see `doc/ROADMAP.md` for the stage order, identity management comes last).
  So nodes only offer externally what is already allowed to be public.
